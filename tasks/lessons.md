## Lessons

### Project organization (per-part folders + catalog)
- 2026-06-29 — **Each part now owns a folder `projects/<slug>/`** holding all its files (source, renders, STL/STEP, G-code, data), gitignored; the repo tracks only `projects/index.tsv` (the catalog) + `projects/README.md`. Manage via `scripts/project.sh` (`new`/`ls`/`show`/`render`/`reindex`/`path`/`rm`). The slug *is* the identity — files are named `<slug>.*`. `slice.sh`/`print.sh` resolve `projects/<slug>/` and fall back to legacy `out/<slug>/`. → Start parts with `project.sh new <slug>`; "go back to <part>" = `project.sh show <slug>`. Don't put part sources back under `models/` or check artifacts into git.
- 2026-06-29 — **macOS ships bash 3.2 — no `declare -A`.** `project.sh reindex` first used bash associative arrays and died with `declare: -A: invalid option` under `/usr/bin/env bash`. → Do map/merge work in **awk** (native assoc arrays, version-independent); discriminate the two input files by `FILENAME==FACTS` (not `NR==FNR`, which misfires when the first file is empty).
- 2026-06-29 — **Bridge rewired to `projects/<slug>/` (done).** `bridge/app.py` now mounts `/files` on `projects/` and serves nested `/files/<slug>/<file>`, scans `projects/*/*.png`, keys model identity on the slug (folder name), and `ensure_stl` exports from `projects/<slug>/<slug>.{scad,py}` (CadQuery `.py` runs to export). `render.sh`'s default outdir is now the model's own folder, so `render.sh projects/<slug>/<slug>.scad` lands PNGs+STL in place. Persona + `--allowedTools` updated (added `project.sh`). The bridge has **no `--reload`**, so code changes need `scripts/stack.sh restart`. → **Still pending:** `/find-model` downloads to `models/downloads/` and renders to a non-`projects/` dir, so find-model results don't surface in the chat UI — relocate its download/render into `projects/<slug>/` next.

### Web/voice bridge (Open WebUI → headless Claude Code)
- 2026-06-24 — **Stream died on image reads** (Open WebUI showed `TransferEncodingError: Not enough data to satisfy transfer length header`). `claude -p --output-format stream-json` emits one JSON object *per line*; a line carrying a read image exceeds asyncio's 64 KiB readline default → `ValueError: Separator is not found, and chunk exceed the limit` → the SSE generator crashes mid-stream. → Pass a large `limit=` (we use 16 MiB) to `asyncio.create_subprocess_exec`, and wrap any SSE generator so it always emits a final stop chunk + `[DONE]` even on error — never let it truncate the HTTP response.
- 2026-06-24 — **Images didn't appear even when renders already existed.** The bridge only attached previews whose mtime *changed* that turn, so "show me the existing renders" surfaced nothing. → Also surface preview PNGs the assistant *reads* this turn (track `Read` tool_use on `out/preview/*.png`), not just re-rendered ones. Image URLs must use `localhost:8765` (the browser runs on the host); `host.docker.internal` only resolves *inside* the container and is for the API connection. Base64-inline images render buggily in Open WebUI — serve URLs.
- 2026-06-24 — **`--allowedTools` wildcard syntax.** `Bash(bash scripts/render.sh *)` (space-star) does NOT match — render was blocked. → Use `Bash(prefix:*)` (colon-star), and cover the cwd-relative forms the agent actually uses (`bash scripts/render.sh:*`, `scripts/render.sh:*`) since `claude -p` runs with cwd=project root. Keep `print.sh`/Moonraker OUT of the allowlist so the physical-print gate holds through the UI.
- 2026-07-04 — **Open WebUI reskin mechanics (Meshy-clone build).** Open WebUI has no theming system, but `/app/build/index.html` links `/static/custom.css` — a bind-mounted CSS file at `/app/build/static/custom.css` is auto-loaded, no image rebuild. Gotchas: static files are **copied to the serving dir at container start** (`open_webui/config.py`) → CSS edits need `docker restart grifcad-openwebui` + hard refresh; never mount into `/app/backend/open_webui/static/` (the startup copy fights it); pin the image **by digest** when CSS targets its DOM; `WEBUI_NAME=X` renders "X (Open WebUI)"; **never `CUSTOM_NAME`** (phones home to api.openwebui.com); env-var settings like `DEFAULT_PROMPT_SUGGESTIONS` seed a *fresh* volume only — an existing `webui.db` wins, so per-model names/avatars/suggestions are one-time Admin-UI steps. Set Task Model (External) to `grif-cad` so background title/tag tasks don't burn opus or pick a parked mode's canned reply as a title.
- 2026-07-04 — **Modes = model ids.** Meshy-style modes (3D Agent / Text to 3D / Image to 3D / parked tiles) are implemented as five ids from the bridge's `/v1/models`, so the Open WebUI picker is the mode switcher and everything stays git-tracked in `bridge/app.py` (not trapped in webui.db). Parked ids short-circuit with a canned reply in **both** stream and non-stream paths (background tasks post `stream:false`). Session keys must include the model id + image digests — text-only sha1 made photo-first chats collide on `sha1("")`. Uploaded reference images go to top-level `uploads/` (content-hash names), NOT under `projects/` (previews glob `projects/*/*.png` and `reindex` would ingest the folder); subprocess readline `limit=` raised to 32 MiB because a Read of a 10 MB image echoes ~13.7 MB of base64 on one stream-json line.
- 2026-06-24 — **Headless billing.** `claude -p` uses the logged-in **subscription** when no `ANTHROPIC_API_KEY` is set; setting that env var silently forces metered API billing. → The bridge unsets `ANTHROPIC_API_KEY` and relies on `CLAUDE_CODE_OAUTH_TOKEN` (`claude setup-token`). Default model `sonnet`, not Opus, to spare plan quota.

### Voice (Chatterbox TTS — JARVIS clone) `VOICE`
- 2026-07-04 — **Install facts (Mac M-series).** Python **3.12.13 worked** despite the upstream README claiming "3.10 required" — every wheel (torch 2.5.1, torchvision, onnx 1.16) resolved on arm64/cp312; setup.sh still auto-falls-back to 3.10. `chatterbox-v2 @master` is unpinned upstream — resolved and pinned to `cc0357396d9c73fc1e6c544ee40bb596020edd09` (includes the MPS float64 fix). **protobuf clash:** descript-audiotools pins `<3.20`, onnx needs `>=3.20.2` → post-install `--no-deps --force-reinstall protobuf>=4.25.0` (resolved 7.35.1; upstream's start.py does exactly this). → Never `--quiet` the pip steps in an installer — it swallowed the real error and cost a debug round-trip.
- 2026-07-04 — **MPS gotcha: torchaudio's sinc resampler dies on MPS** (`Output channels > 65536 not supported`, torch 2.5.1) and `PYTORCH_ENABLE_MPS_FALLBACK=1` does NOT rescue it (op is "implemented", just capped — fallback never fires). Only call site is chatterbox's `get_resampler()` (reference-audio prep) → `voice/setup.sh` patches it to run that one op on CPU (marker `grifcad-mps-patch`; upstream precedent: start.py post-install patches). Keep the env var in the launcher anyway — harmless, catches genuinely unimplemented ops.
- 2026-07-04 — **Server facts (pinned f0afcc6d).** Health route: `GET /api/ui/initial-data`. Config keys: `server.port`, `tts_engine.device`, `tts_engine.reference_audio_path` (absolute path works). Model `chatterbox-turbo` loads onto MPS at *server start*; weights land in the HF cache (`~/.cache/huggingface`), not `model_cache/`. Voice = bare filename in `reference_audio/` via the request's `voice` field.
- 2026-07-04 — **Reference-clip findings.** Winner: **4:36–4:56** of the source MP3 (alts: 7:30, 5:20 — Grif A/B'd by ear). Algorithmic pre-screen that worked: 100 ms RMS frames → windows scored by count of ≥200 ms silence gaps (speech phrasing), active-frame dynamics (std/mean), and pause-ratio 8–45%; music/SFX beds score near zero gaps. 20 s mono 16-bit 44.1 kHz via `afconvert` (no ffmpeg needed).
- 2026-07-04 — **Measured latency (M5, MPS).** First request after server start ≈ **68 s** (kernel warmup) — then **10–27 s** for a two-sentence line; one sentence via the Open WebUI proxy ≈ **15 s** incl. MP3 transcode. Slower than the 2–6 s/sentence estimate; `SPLIT_ON=punctuation` still makes perceived start = first sentence. Warmup means the FIRST read-aloud after a restart feels slow — that's normal.
- 2026-07-05 — **The "read-aloud disconnects" + "stuck in listening" bugs were ONE root cause: the Colima VM's default 2 GiB memory.** Loading faster-whisper for STT pushed the Open WebUI container past the VM's total RAM → kernel `global_oom` killed the python process (proof: `colima ssh -- sudo dmesg | grep -i oom`; container RestartCount was 11) → container restarted → every websocket dropped ("multiple disconnects") and the transcription result never arrived ("stuck in listening", no error logged — the process that would log it died). Fix: `colima start --memory 6 --cpu 4` (persists in the profile; `ensure_colima` now sizes new VMs). After resize: STT = 1.0–1.5 s/sentence, container at ~1.2/5.8 GiB with whisper loaded, restarts 0. → When a Dockerized UI "randomly disconnects", check `docker inspect -f '{{.RestartCount}}'` and the VM's dmesg before debugging the app.
- 2026-07-05 — **TTS_BF16=on is fatal on MPS — do not retry.** The engine's autocast is hardcoded `torch.autocast("cuda", …)`, which is a no-op on MPS ("CUDA is not available. Disabling"), so fp32 activations hit the bf16-converted T3 weights and MPSGraph aborts the whole process on the first request (`'mps.add' op requires the same element type`, torch 2.5.1). `VOICE_BF16` stays `off` in config/voice.env; the plumbing is kept for a future CUDA/newer-torch box.
- 2026-07-05 — **No Open WebUI timeout was ever in play.** `AIOHTTP_CLIENT_TIMEOUT` unset → `None` → the shared aiohttp session waits forever on `/api/v1/audio/speech`. The "dead" feel was cold-start (~68 s) + OOM restarts, not a proxy timeout. Also measured: the Chatterbox server blocks its whole event loop during synthesis (health probes get no response until generation finishes), so `stack.sh check` can false-negative while a read-aloud is generating; queued chunks still complete (3 concurrent sentences ≈ 11.5 s warm). Warm latency ≈ audio duration (~5–7 s/sentence on M5 MPS) — near real-time is the physics; `start_voice` now fires a detached pre-warm (`warm_voice`) so the first click never pays the 68 s.
- 2026-07-05 — **The voice server unconditionally `webbrowser.open()`s its own UI at startup** (no config flag in pinned f0afcc6d). Suppressed env-level, no upstream patch: `BROWSER=/usr/bin/true` in the stack.sh launch line makes Python's webbrowser module run `/usr/bin/true <url>` instead of opening a tab.
- 2026-07-04 — **Open WebUI audio config API.** With `WEBUI_AUTH=false`: `GET /api/v1/auths/` 401s, but `POST /api/v1/auths/signin` with **empty** creds returns the admin bearer token. And the compose `AUDIO_TTS_*` seed DID apply to our *existing* volume — PersistentConfig only wins where a key was previously written; audio had never been configured, so recreating the container with the new env block was enough. `/api/v1/audio/config` confirms; `POST …/config/update` never needed.

### Toolchain / install (macOS Apple Silicon)
- 2026-06-24 — **OpenSCAD stable cask is ancient.** `brew install --cask openscad` installs the 2021.01 Intel build, which macOS kills on launch (`Killed: 9`) under Rosetta. → Use `brew install --cask openscad@snapshot` (arm64-native, current). `render.sh` globs `/Applications/OpenSCAD*.app` for the binary.
- 2026-06-24 — **Removing OrbStack breaks Docker.** A stale `credsStore: osxkeychain` left in `~/.docker/config.json` points at OrbStack's now-missing helper → image pulls fail (`docker-credential-osxkeychain not found`); and brew's `docker` CLI needs `cliPluginsExtraDirs` for `docker compose` to resolve. → `setup.sh` fixes both (drops a `credsStore` whose helper isn't on PATH; adds the brew cli-plugins dir). `host.docker.internal` works on Colima/Lima for container→host (the earlier worry was unfounded).

### Slicers
- 2026-06-24 — **OrcaSlicer vs Creality Print.** Only OrcaSlicer is reliably scriptable on macOS (headless `--slice` CLI; ships built-in K2 Plus profiles). Creality Print (v7.1, an Orca fork) has a CLI but it's undocumented + crash-prone on Mac → treat as **open-in-GUI only** (`open -a "Creality Print" <file>`). Profiles use **incompatible variable names** despite shared lineage — NOT interchangeable; keep them as separate profile worlds. → Slicer choice is a per-person preference governing the GUI-launch button (both shown; `SLICER_DEFAULT` orders them); headless `/slice` stays OrcaSlicer; printing is slicer-agnostic (Moonraker). Neither has a headless network-print CLI.
- 2026-06-24 — **No xvfb on macOS.** `xvfb-run` is Linux-only — the slice path must call the OrcaSlicer bundle binary directly on Mac (`/Applications/OrcaSlicer.app/Contents/MacOS/OrcaSlicer`). `scripts/slice.sh` now adds `xvfb-run` only when `uname` = Linux.
